Lesson 0003
Workflow + 人類 handoff · Human Input 轉真人客服

🎯 這課的 win
90 分鐘後，你的「瓦斯客服 Chatflow」會從「緊急情況丟 SOP」升級成「整包對話暫停、寄 Email 給值班客服、值班人員在 form 標記接手後 AI 自動回覆客戶」。你會親眼看到 Chatflow 真的 pause + resume（不是 call LLM 一次就結束）。

為什麼 Lesson 3 不直接做 Agent / Tool / API？

你的 mission 是「多租戶 SaaS AI 客服」。「客服」的本質是 human-in-the-loop：AI 能答 80%，剩下 20% 必須能轉真人。沒學 Human Input 之前做 Agent / Tool / API = 蓋空中樓閣。Lesson 3 是「客服系統的脊椎」，Lesson 4-6 才長四肢。

⚠️ Lesson 2 的「緊急分支」其實不算客服

你 Lesson 2 做的「緊急 Answer node」只是「丟個 SOP 給客戶自己看」——沒有任何真人會接到這個 case。生產環境的客戶打電話來是因為「真的需要人來」，純丟 SOP 是「逃跑」不是「客服」。Lesson 3 修這個洞。

先決條件

  • Lesson 0002 完成：「瓦斯客服 Chatflow」5 node 跑得起來、4 種 query 都分流正確
  • Dify 帳號還活著：能進 http://localhost admin / Studio
  • Email delivery 設定想好：本課用 Email delivery（不需要真人客服有 Dify 帳號），你只要想好「值班客服的 email 是誰」
  • （建議）準備一支可寄 SMTP 的 Email：self-host Dify 預設 SMTP 沒設，會寄不出去；先用 resend.com / SendGrid / Gmail SMTP 任一個，或進 Settings → Email 確認能寄測試信
  • （Step 5 需要）你的 Dify app API key（Studio → 你的 App → API Access）
  • 預估時程：90 分鐘（含 Email 設定 + form preview 驗證 + curl SSE 預習）
Email SMTP 還沒設定？快速 recipe（Resend 為例）

進 Settings → Email → 選 Resend 或 SMTP。Resend 免費 100/天、SMTP host = smtp.resend.com、port 587、user = resend、password = 你的 Resend API key。存檔後按 Send Test Email 確認能收到——沒確認就不要進 Step 2，否則 Step 4 會卡「人根本沒收到信」。

Step 1 — 打開 Lesson 2 的 Chatflow

  1. 進 Studio → 點「瓦斯客服 Chatflow」→ Edit
  2. 你會看到 Lesson 2 的 5 node：Start → Question Classifier → 3 個 Answer 分支（瓦斯相關 → KB → LLM → Answer / 不相關 → Answer / 緊急 → Answer）
  3. 在 緊急 → Answer 那條線上，把 Answer node 標記「待刪」——我們要用 Human Input 取代它
  4. （不要真的刪，先拉 Human Input 進來再刪，避免中途連線壞掉）

1.1 確認 Start 跟 Question Classifier 設定還在

打開 Question Classifier，確認 3 個類別 instruction 還在（Lesson 2 設的「瓦斯相關 / 不相關 / 緊急」）。沒掉就別動。

Step 2 — 加 Human Input Node

從 node palette 拉 Human Input 進 canvas，拖到「緊急」分支下方。把 Question Classifier 的「緊急」出口接到這個新 node。

2.1 Delivery Method — 選 Email

為什麼選 Email 不用 WebApp？

WebApp delivery 是「對話窗直接彈 form」——只對「正在跟你對話的客戶」有用。但「真人客服」通常不在 WebApp 前。Dify 預設 WebApp form 還有一條限制：triggered workflow 不可用（你的 Chatflow 是 conversational 所以 OK，但 Email 更泛用）。Email 寄到值班客服的信箱，客服在任何地方點開就能接手。

  • Delivery method：選 Email
  • Recipients：填值班客服 email，例如 oncall@your-gas-company.tw（多人用逗號分）
  • Email subject 預設會帶 workflow 變數，本課用預設即可

2.2 Form Content — Markdown + 動態變數

Form 內容寫 Markdown，把對話 context 帶給真人客服：

# ⚠️ 緊急瓦斯客服 case

客戶訊息：
> {{sys.user_query}}

對話時間：{{sys.timestamp}}

請值班客服接手後填寫下方欄位，並按下對應按鈕。
為什麼 form 裡要把 user_query 跟 timestamp 帶進來？

真人客服收到信打開 form，必須馬上知道客戶說了什麼、什麼時候說的。這兩個是 Human Input form 內建可引用的 sys variables。Workflow 變數用 {{var}} 直接 render 在 form Markdown 裡——不需要先接 Answer 或 Output node（這是 Human Input 跟其他 node 最大的差別）。

2.3 Form Fields — 兩個欄位

欄位名型別為什麼
handling_status Select（必填） 值班客服的回報選項：已聯繫客戶 / 預約到場 / 已派工 / 已排除
handling_note Paragraph（選填） 備註，例：「客戶在台北市信義區 OO 路，10 分鐘後聯繫」「預約明早 9 點到場」
⚠️ Select 必填 / Paragraph 選填

Dify 規則：Select / File / File List 是必填（form 按鈕會 disable 直到填），Paragraph 選填。不要把 handling_status 改成 Paragraph——客戶按送出後下游 If-Else 沒值會 crash。

2.4 User Action — 兩個按鈕

按鈕標題Action ID下游接到哪style
已接手 handled Answer node（回覆客戶） primary
無法處理 unhandled LLM node（AI fallback 回覆） default
Action ID 命名原則

Dify 會把 action ID 跟 title 分別 expose 給下游：__action_id（機器讀，例 handled）+ __action_value（人讀，例 已接手）。下游 If-Else 條件寫用 __action_id（永遠英文、stable）——別用 __action_value，改 title 就壞。

2.5 Timeout Strategy — 縮短為 30 分鐘

  • Expiration：30 minutes（不要 default 3 days——緊急 case 等 3 天出事上新聞）
  • Timeout branch：必須接一個 Answer node（內容：「目前客服繁忙、請撥 119」），不然 timeout 後 workflow 直接結束客戶沒收到任何回覆

Step 3 — 串好分支

最終的 flow 結構（這次擴充 Step 5 的「緊急」分支）：

[Start]
   ↓
[Question Classifier]
   ├─ "瓦斯相關問題" → [Knowledge Retrieval] → [LLM] → [Answer]
   ├─ "不關瓦斯"     → [Answer (拒絕範本)]
   └─ "緊急"         → [Human Input (Email)]
                          ├─ "已接手"     → [Answer (回覆客戶)]
                          ├─ "無法處理"   → [LLM (fallback)] → [Answer]
                          └─ timeout 30m  → [Answer (119)]

3.1 「已接手」分支 Answer node

直接接一個 Answer node，內容：

已收到 ✅

我們的值班客服已接手您的 case，並會盡快與您聯繫。

如有任何變化（瓦斯味加劇、出現頭暈），請立即撥 **119** 或本公司 24 小時搶修專線。

📋 您的處理編號：#{{human_input.handling_status}}-{{sys.conversation_id}}

3.2 「無法處理」分支 LLM + Answer

LLM node 設 fallback 答覆，system prompt：

你是瓦斯公司 AI 客服。值班客服剛剛標記「無法處理」這個緊急 case。
請給客戶一個禮貌的 fallback 回覆，引導他們撥打真人專線或 119。

客服備註：{{human_input.handling_note}}

【限制】
- 不要假裝有人會來接手
- 必須明確給出真人專線號碼 + 119
- 不要編造預計到場時間

下游接一個 Answer node 引用 LLM 的 text。

3.3 Timeout branch Answer node

簡短緊急 fallback：

我們已收到您的緊急通報，但目前值班客服較繁忙，無法立即回應。

請您立即採取以下任一行動：
1. 撥打 **119** 求助
2. 撥打本公司 24 小時搶修專線：<您的專線>
3. 遵循「禁、關、推、離」SOP（不可開電器、關總閥、通風、撤離）

我們會再嘗試聯繫您。

Step 4 — Publish + WebApp 測試

  1. 右上 Publish → Publish Update
  2. 左側 Studio → 「瓦斯客服 Chatflow」點 Preview
  3. 輸入 query：家裡聞到很重的瓦斯味怎麼辦？
  4. 預期：
    • Question Classifier 把它分到「緊急」
    • Human Input node 把 form link 寄到值班客服 email（這就是為什麼 Step 0 要先驗證 SMTP）
    • WebApp 顯示「客服正在處理、請稍候」（不會立刻回 SOP——這跟 Lesson 2 不同）
  5. 到 Email 信箱點 form link → 填欄位 → 按「已接手」或「無法處理」
  6. 回到 WebApp 看 AI 自動回覆

4.1 驗證清單（WebApp 端）

情境測試 query預期結果
緊急 + 真人已接手 廚房有瓦斯味 Email 寄出 → 真人按「已接手」→ WebApp 顯示「值班客服已接手」+ 處理編號
緊急 + 真人無法處理 懷疑瓦斯中毒怎麼辦 Email 寄出 → 真人按「無法處理」+ 填備註 → WebApp 顯示 AI fallback（提到 119）
瓦斯相關（複習 Lesson 2） 瓦斯帳單過期還能去超商繳嗎 走 KB + LLM，正常回答（Lesson 2 flow 不變）
不相關（複習 Lesson 2） 今天台北天氣如何 走拒絕範本（Lesson 2 flow 不變）
Email 沒收到？先查這 3 個地方

1. Dify 後台 Logs（右上鈴鐺 → Logs → 看 workflow run 是否跑到 Human Input）；2. SMTP 設定（Settings → Email → Send Test Email 確認能寄）；3. Spam folder（resend / Gmail 很容易進 spam）。三者皆查過仍沒信，看 docker compose logs worker 找 SMTP 錯誤。

Step 5 — curl API 預習：看 workflow 真的 pause

這一步是 Lesson 6（後端整合）的暖身

Lesson 6 會用 FastAPI 把 Dify 包進自家後端。本步先讓你「親眼看到」Chatflow 真的是 pause + resume，不是 call LLM 一次就回完。這是你身為 backend engineer 的視角——Dify API 是 long-running 的，前端必須能 handle 5 秒以上的 pause。Lesson 6 會展開細節。

5.1 準備 API key 跟 app ID

  • Studio → 瓦斯客服 Chatflow → 右上 API Access → 複製 API Key
  • App ID 在 URL（/app/<APP_ID>/workflow）

5.2 curl SSE stream 看 pause event

curl -N -X POST "http://localhost/v1/chat-messages" \
  -H "Authorization: Bearer <YOUR_API_KEY>" \
  -H "Content-Type: application/json" \
  -d '{
    "inputs": {},
    "query": "我家瓦斯味很重",
    "user": "ryo-test-user",
    "response_mode": "streaming"
  }'

看 SSE stream 輸出，預期會看到：

  • event: workflow_started
  • event: node_started（Question Classifier 開始）
  • event: node_finished（Classifier 結束，分到「緊急」）
  • event: node_started（Human Input 開始）
  • event: human_input_required（workflow pause 在這裡，帶 form_token）

複製 form_token，下一步用。

5.3 手動 submit form 模擬「值班客服按已接手」

curl -X POST "http://localhost/v1/form/human_input/<form_token>" \
  -H "Authorization: Bearer <YOUR_API_KEY>" \
  -H "Content-Type: application/json" \
  -d '{
    "inputs": {
      "handling_status": "已聯繫客戶",
      "handling_note": "10 分鐘後會 call 客戶"
    },
    "action": "handled",
    "user": "ryo-test-user"
  }'

回 {} 表示成功。SSE stream（如果你還在連）會繼續 emit 後續 node event。

Quiz — 取回長期記憶

Q1. Human Input node 跟 Answer node 最大的差別是什麼？

Human Input 跟 Answer 表面看都「輸出文字」，但 Human Input 會把 workflow pause 住，等真人表單送出後才 resume。背後是 workflow_runs API 的 long-running 機制（form_token / human_input_required event）。Lesson 6 會展開這個設計。

Q2. 緊急客服 case 為什麼 timeout 不能用 Dify 預設的 3 days？

Default 3 days 適合「內部審稿」「審批流程」這類可以等的 case。緊急客服的 SLA 是「分鐘級」，30 分鐘 timeout + 接 Answer fallback 是合理的設計。Timeout 不是技術限制，是業務承諾。

Q3. 下游 If-Else 條件應該用 __action_id 還是 __action_value？

__action_id 是機器讀的 stable identifier（例 handled），改 button title 不會影響下游邏輯。__action_value 是 display 給人看的（例「已接手」），改 title 下游就壞。Rule of thumb：所有 if/else condition 都用 id。
