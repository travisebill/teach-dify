Lesson 0002
Customer Service Bot with Knowledge Base · RAG 入門

🎯 這課的 win
90 分鐘後，你會有一個跑在自己 Dify 的「瓦斯客服 Chatflow」——能用台灣天然氣公司真實 FAQ（20 條 Q&A、5 大類）回答用戶問題、分流不相關主題、上線前跑過 Recall Test 驗證 retrieval 準確率。

為什麼用 Chatflow 不用 Chatbot？

Lesson 1 的 Hello Dify 是 Chatbot（只有 system prompt + LLM）。本課做 Chatflow——多 node 串接，能對問題分流（瓦斯相關 → 查 KB → LLM 整合回答；無關 → 直接拒絕）。這是 Chatbot 辦不到的，是 real customer service bot 的核心 pattern。

⚠️ 重要：Recall Test 不跑不要上線

RAG chatbot 上線前沒跑 Recall Test 等於盲飛。SKILL 永久教訓：「KB 建好的第一件事是到 Retrieval Testing 拿幾個真實 query 測試，看到 top chunks 真的是相關 FAQ 才能進下一個 step。」

先決條件

  • Lesson 0001 完成：Docker Dify 跑得起來、provider 設定過、有 Chatbot App
  • Embedding model provider 已加：Lesson 1 加的「LLM provider」不夠——embedding model 是另一個 setting，這課要再加（見 Step 0）
  • FAQ 檔準備好：本課用你提供的 reference/gas-company-faq.md（20 條 Q&A，5 大類）
  • 預估時程：90 分鐘（含 Recall Test + 4 種測試情境驗證）

Step 0 — 加 Embedding Model Provider

Embedding model 是什麼？

RAG 把文件切成 chunk，用 embedding model 把每個 chunk 轉成向量存起來。使用者問題進來也轉成向量，比較相似度找出最相關的 chunks。Embedding 跟 LLM 是兩個不同 model——Lesson 1 加的「Default Reasoning Model」是 LLM，這課要另外加 Embedding。

進 Settings → Model Provider，往下捲找 TEXT EMBEDDING 區段，挑你準備好的 provider 加：

路徑 A — Native Cohere Provider（如果 API key 是真 Cohere 或代理）

  1. 選 Cohere → 填 API Key → 儲存
  2. 推薦模型：embed-multilingual-v3（支援繁中，本課 FAQ 是繁中內容）
  3. 不要選 embed-english——會大幅降準確率

路徑 B — Custom OpenAI-compatible（你的 MiniMax.io 通常走這條）

為什麼 MiniMax 走 OpenAI-compatible？

MiniMax.io 的 https://api.minimax.io 通常 expose OpenAI-compatible REST endpoint（/v1/embeddings）。Dify 的「Custom」provider 允許設定任意 base URL，等於把 MiniMax 的 embedding endpoint 當自家 provider 用。

  1. 選 OpenAI-API-compatible（在 Custom 區段）
  2. 填 Name：MiniMax
  3. Base URL：https://api.minimax.io/v1
  4. API Key：你的 MiniMax token（不需要加 Bearer 前綴，Dify 會自己加）
  5. Model name：填 MiniMax 提供的 embedding model（查 MiniMax 文件，常見是 embo-01 之類）
  6. 儲存

驗證

無論走 A 或 B，回 Model Provider 主頁應該看到至少 1 個 provider 同時有 LLM + TEXT EMBEDDING 兩個 label。

Step 1 — 建 Knowledge Base（KB）

  1. 頂部 menu 點 Knowledge → 右上 Create Knowledge
  2. 選 source type：Import from file（FAQ 是 .md）
  3. 選你的本機 gas-company-faq.md（從 teach-dify workspace reference/ copy 到本機，或者直接從 workspace 拉）
  4. KB 名稱填：瓦斯客服 FAQ
  5. 進 Index Method 設定頁（下一步處理）

Step 2 — 設定 KB 處理參數

本課用的設定（已驗證適合 20 條 FAQ）

官方文件列了一堆選項，新手看一頭霧水。本課設定是針對 20-30 條 Q&A 的最佳實踐——別的設定都先不動。

  • Chunk Settings：預設 Automatic（依段落自動切）。FAQ 已經是 Q1~Q20 結構化，切出來每 chunk 就是 1 條 Q&A，剛好。
  • Index Method：選 High Quality（會用 embedding model，多花 token 但 KB recall 準確度大幅提升）
  • Embedding Model：選 Step 0 加的那個（embed-multilingual-v3 或 MiniMax 的 embedding model）
  • Retrieval Settings：選 Hybrid Retrieval（vector + full-text 一起，semantic 70% / keyword 30% 是常見權重）

按 Save and Process。Dify 會跑 chunking → embedding → indexing。等 status 變 completed（20 條 FAQ 通常 30-60 秒）。

Step 3 — Recall Test（永久教訓必跑）

進 KB 詳情頁，左側 menu 點 Retrieval Testing。試 3 個 query 看 top chunks 是否正確：

Query預期 Top-1 Chunk
瓦斯帳單過期還能去超商繳嗎Q1 的 A1（提到「7-11、全家、萊爾富、OK」）
微電腦瓦斯表閃紅燈Q8 的 A8（提到「黑色復歸鈕」）
瓦斯爐火黃紅色Q15 的 A15（提到「正常是藍色」「爐頭積碳」）
3 個都對才進下一步

如果有任何一個 top chunk 是錯的（例如 Q15 查「黃紅色」卻撈到 Q4「基本費」），代表 chunking 或 retrieval 設定要調。常見解法：換 embedding model / 調 hybrid weights（semantic 拉到 80%）/ 把 KB 文件再人工標段落。

Step 4 — 建 Chatflow App

為什麼這次是 Chatflow 不是 Chatbot？

Chatbot 只能「一個 LLM 接 user input」。Customer service 必須分流：瓦斯問題 → 查 KB + LLM 整合；不相關 → 直接拒絕；緊急 → 直接轉真人（Lesson 3 會做）。這需要 conditional branching——只有 Chatflow 辦得到。

  1. 進 Studio → Create from Blank → 選 Chatflow
  2. 命名：瓦斯客服 Chatflow
  3. 進 canvas。預設已有 Start + Answer 兩個 node——先刪掉預設的 Answer，重新從頭接

Step 5 — 串接 5 個 Node

本課最終的 flow 結構（依官方 tutorial）：

[Start]
   ↓
[Question Classifier]   ← 用 LLM 對 user 輸入分流
   ├─ "瓦斯相關問題" → [Knowledge Retrieval] → [LLM] → [Answer]
   ├─ "不關瓦斯 / 客服指引" → [Answer] (拒絕範本)
   └─ "緊急情況 / 轉真人" → [Answer] (緊急指引)

5.1 Question Classifier Node

  • 從 Question Classifier 加入
  • Input variable：sys.user_query（User Input / 對話輸入）
  • Model：Lesson 1 設的 LLM（用好的 LLM——classifier 對模型品質敏感）
  • 設定 3 個分類（Instruction 寫清楚區別）：
類別Instruction 寫法範本
瓦斯相關問題 用戶問任何關於瓦斯帳單、抄表、安全操作、瓦斯表安裝 / 異動、爐火熱水器異常等 跟台灣天然氣股份有限公司服務相關的問題
不關瓦斯 用戶問的問題跟瓦斯／天然氣完全無關，或聊天／打招呼 / 跟閒聊無關的主題（天氣、新聞、政治、其他公司產品等）
緊急情況 / 轉真人 用戶提到漏氣、火警、瓦斯中毒、搶修、瓦斯管線被挖斷等需要立即人為介入的緊急狀況

5.2 兩條 Direct Reply 路徑（Answer node）

拉一個 Answer node 接 不關瓦斯 分支。內容：

您好，我是瓦斯公司的 AI 客服助手 🤖

我能協助您：
- 帳單繳費問題
- 抄表與度數查詢
- 安全與緊急處理指引
- 瓦斯表異動 / 過戶申請
- 爐火 / 熱水器使用異常排除

您問的問題不在我的服務範圍內。若有其他瓦斯相關需求，歡迎詢問！

再拉一個 Answer node 接 緊急情況 分支。內容：

⚠️ 緊急處置 SOP
⚠️ 您描述的狀況可能涉及漏氣或緊急危險，請立即遵循「禁、關、推、離」：

1. **禁**：不可開關任何電器（避免火花）
2. **關**：立即關閉瓦斯表前總閥
3. **推**：輕推窗戶通風
4. **離**：迅速撤離至室外安全處

📞 並撥打本公司 24 小時緊急搶修專線，或撥打 **119** 求助。

我已將您的訊息標記為【緊急】送出，請等待真人客服優先聯繫您。

5.3 Knowledge Retrieval + LLM（核心）

從 瓦斯相關問題 分支往下：

  1. 加 Knowledge Retrieval node
    • Query variable：sys.user_query
    • Knowledge base：選 瓦斯客服 FAQ（Step 1 建的那個）
  2. 加 LLM node
    • Model：Lesson 1 設的 LLM
    • Context：Knowledge Retrieval / result（KB 撈到的 chunks）
    • System prompt 寫法：
你是台灣天然氣股份有限公司的 AI 客服助手。基於以下「已確認的官方 FAQ 內容」回答用戶問題：

【參考內容開始】
{{context}}
【參考內容結束】

【用戶問題】
{{sys.user_query}}

【回答規範】
- 引用 FAQ 內容時要具體（如提到「瓦斯表復歸」要帶出步驟）
- 不知道就明確說「建議聯繫客服專線」
- 不要編造條款或數字（基本費、復歸時間等都要照 FAQ）
- 用繁體中文、台灣用語（「瓦斯」不要寫「燃氣」）
  1. 加最後一個 Answer node 接 LLM 輸出
  2. Output variable：選 LLM 的 text 輸出

Step 6 — Publish + WebApp 測試

  1. 右上 Publish → Publish Update
  2. 左側 Studio → 瓦斯客服 Chatflow 卡片點 Visit WebApp 或 Preview
  3. 逐個測 4 種情境：
情境測試 query預期結果
瓦斯相關 瓦斯帳單過期還能去超商繳嗎？ KB 撈到 Q1 → LLM 整合回答，提到「7-11、全家、萊爾富、OK」
瓦斯相關（專業術語） 微電腦瓦斯表跟傳統表有什麼差別？ KB 撈到 Q7 → 提到「微量漏氣」「超時」「強震 5 級以上」三大防護
不相關 今天台北天氣如何？ 直接走「不關瓦斯」Answer node，禮貌拒絕
緊急 家裡聞到很重的瓦斯味怎麼辦？ 走緊急 Answer，給「禁關推離」SOP + 119
4 種都對才進下一步

如果瓦斯相關的查詢有 LLM 自己編造（例如基本費數字寫錯），代表 system prompt 沒強調「不要編造」or KB 撈到的 context 不對。回 Step 3 重新跑 Recall Test 確認。

  • Chatflow 瓦斯客服 Chatflow 已建，5 node 串接正確（Classifier → Answer/KB→LLM→Answer）
  • Question Classifier 3 個類別設定（瓦斯相關 / 不相關 / 緊急）
  • Publish 後 WebApp 上跑 4 種 query 都正確分流

Quiz — 取回長期記憶

做 retrieval practice，把今天的關鍵字釘在腦海：

Q1. 為什麼 Lesson 2 用 Chatflow 不用 Chatbot？

Chatbot 也能接 KB（AI 自己決定用不用），但客服需要明確分流：瓦斯相關 → 查 KB；不相關 → 直接拒絕；緊急 → 轉 SOP。這要 Question Classifier——只有 Chatflow/Workflow 才有。RAG 的關鍵不是 KB 本身，是「該不該用 KB」的 conditional 控制。

Q2. KB 建好但上線前沒跑 Recall Test，最可能發生什麼事？

Recall Test 是 RAG 的「unit test」。沒測就上線 = 盲飛。最常見的失敗：embedding model 跟你的文件語言不匹配、chunk 切錯邊、hybrid weight 偏一邊。永久教訓：KB 建好的第一件事是 Recall Test。

Q3. 「Hybrid Retrieval (semantic 70 / keyword 30)」的意義？

Vector retrieval（語意）抓「概念相近」、full-text retrieval（keyword）抓「精確字」. 純 vector 會漏精確技術詞（例如「復歸鈕」），純 keyword 會漏意譯問法。Hybrid 是最佳平衡點。本課 FAQ 有技術詞（復歸鈕 / 微電腦瓦斯表 / 萊爾富）適合偏 vector 70% setup。
